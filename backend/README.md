# kabuka backend

日本株予測・売買シグナル kabuka のバックエンド。
チーム調査（J-Quants / 予測モデル / バックテスト / 批判役）の推奨に従い、
**まず ¥0 の無料データでファクターのαを検証**する段階から始める。

## セットアップ

```bash
# リポジトリ直下で
python3.12 -m venv .venv
.venv/bin/pip install -e backend          # pyproject の依存を導入
```

## 無料データ・ファクターバックテスト（一次検証）

```bash
cd backend
../.venv/bin/python -m app.ingestion.prices     # yfinanceで株価取得→parquetキャッシュ
../.venv/bin/python scripts/run_backtest.py      # 分位バックテスト実行
```

### データソース（無料スタック）
- **株価(配当・分割調整済)**: yfinance（`code.T`）。10年以上取得可。
- **ベンチマーク**: TOPIX連動ETF `1306.T`（対TOPIX超過αの基準）。
- **財務(value/quality)**: EDINET API v2（無料・要キー）。下記手順で有効化。

### value/quality（EDINET財務）の有効化手順
1. https://disclosure2.edinet-fsa.go.jp/ で無料アカウント作成 → APIキー発行
2. `cp .env.example .env` して `KABUKA_EDINET_KEY=...` を記入
3. 疎通＆抽出確認（パイロット: 直近20営業日・ユニバースの有報のみ）:
   ```bash
   ../.venv/bin/python -m app.ingestion.financials
   ```
   ※決算提出が集中する6月頃を含む期間でないと0件のこともある。抽出列が正しいか確認する。
4. 本収集（期間内を日次スキャン。時間がかかる）→ `backend/data/financials_pit.parquet` 生成
5. `run_backtest.py` を再実行すると value/quality と総合スコアが自動で評価対象に加わる

> 注意: EDINETの要素ID(elementID)は会社・年度で揺れるため、`financials.py` の
> `FIELD_CANDIDATES` は初回実取得後に実データを見て調整する前提（PIT結合は submit_date 基準）。

### 評価設計（批判役の指摘を反映）
- ルックアヘッド回避: 月末tのファクター → 翌月t+1リターンで評価（重複なし月次）。
- 取引コスト織込み: 分位入れ替え turnover に往復コストを控除（既定 片道20bps）。
- 指標: 月次IC / ICIR、分位ロングショート年率・シャープ・最大DD、対TOPIX超過α・勝率。

### 既知の制約（重要）
- ユニバースは**現構成銘柄のみ＝生存者バイアスあり**。数値は上振れ方向。
  有望なら J-Quants Standard 等で時点別構成銘柄(PIT)・廃止銘柄を補完して再検証する。
- 一次合格基準は「絶対20%/15%」ではなく**「対TOPIXαが偶然でなさそうか」**。

## 検証結果（2014–2024, 161銘柄, 片道20bps）

| factor | IC平均 | ICIR | LS年率 | LSシャープ | 対TOPIX超過(ロング) |
|---|---|---|---|---|---|
| mom_12_1 | 0.015 | 0.23 | 1.9% | 0.20 | +5.9% |
| mom_6_1 | 0.020 | 0.35 | 3.5% | 0.31 | +5.0% |
| reversal_1m | 0.025 | 0.47 | 4.9% | 0.42 | +3.7% |
| low_vol | -0.014 | -0.23 | -9.3% | -0.59 | -1.1% |
| **composite**(mom_6_1+reversal) | **0.031** | **0.66** | **6.1%** | **0.56** | +3.7% |

### value/quality 追加後（EDINET財務, 2016–2024, 102ヶ月）

| factor | IC平均 | ICIR | LS年率 | LSシャープ | 対TOPIX超過 | 勝率 |
|---|---|---|---|---|---|---|
| **value_bp**(割安 B/P) | **0.031** | **0.80** | **11.7%** | **1.16** | **+11.6%** | **71.6%** |
| value_ep(益回り E/P) | 0.018 | 0.57 | 2.1% | 0.28 | +7.5% | 58.8% |
| quality_roe | -0.005 | -0.13 | -2.1% | -0.18 | +5.6% | 59.8% |
| quality_margin | 0.002 | 0.06 | -3.0% | -0.24 | +4.5% | 57.8% |
| quality_equity_ratio | -0.004 | -0.08 | -2.2% | -0.09 | +5.2% | 63.7% |
| value_quality(合成) | 0.015 | 0.42 | 0.7% | 0.13 | +5.0% | 64.7% |

**最大の発見**: **バリュー(B/P)が突出**（ICIR 0.80, LSシャープ 1.16, 対TOPIX +11.6%/年, 勝率72%）。
一方クオリティ系(ROE/利益率/自己資本比率)はこの大型株ユニバースでは LS が弱い〜マイナス。
→ 批判役の「日本株はモメンタムでなく**value**が効く」を実データで裏付け。

**統計的有意性 (Deflated Sharpe Ratio)**: 価格のみでは最良composite でも DSR=0.53 だったが、
value_bp 追加後は **DSR=0.885**（11ファクター試行で多重検定補正）。0.53→0.885 と大きく改善したが、
**まだ0.95には届かず**「偶然を完全には否定できない」水準。

**示唆**:
- **バリュー(B/P)が最強**。日本株のファクター構造（valueが効きmomentum/qualityは弱い）を実データで再現。
- 価格ファクターのみではモメンタムは弱く、合成しても DSR=0.53（非有意）。
- value_bp を加えると DSR=0.885 まで改善。バリュー軸が予測力の主柱。
- ただし **生存者バイアスで上振れ・税引前・期間102ヶ月・DSR<0.95**。絶対年率20%/15%の断定はまだ不可。

**コスト感度**: 片道0〜40bpsでLS年率はほぼ不変（ロングショートは両建てでコストが概ね相殺されるため）。
コストが効くのはロングオンリーの対TOPIX超過側。低回転の月次リバランスではコストは主因ではない。

## 生存者バイアス除去版（本検証 / J-Quants TOPIX500・PIT・2016–2024）

時点別TOPIX500構成銘柄（廃止銘柄含む）＋開示日基準PIT財務での結果。ベンチは構成銘柄等加重。

| factor | IC平均 | ICIR | LS年率 | LSシャープ | 超過 | 勝率 |
|---|---|---|---|---|---|---|
| **value_bp** | **0.035** | **0.76** | **8.5%** | **0.78** | +5.3% | 62% |
| value_ep | 0.028 | **0.85** | 5.6% | 0.72 | +4.3% | 66% |
| value_quality(合成) | 0.025 | 0.84 | 4.8% | 0.68 | +4.2% | 71% |
| reversal_1m | 0.021 | 0.42 | 3.7% | 0.37 | -1.4% | 41% |
| mom_12_1 / mom_6_1 | ~0.001 | ~0.02 | ~0 | ~0 | ~0 | - |
| quality各種 | ~0 | ~0.1 | 負 | 負 | ~0 | - |

**DSR（多重検定補正, N=10）**: 最良 value_bp で **0.674**（<0.95）。

### 結論（Go/No-Go）
- ✅ **バリュー(B/P, E/P)のαは生存者バイアスを除いても残った**。ICIR 0.76〜0.85は実務的に有望水準。
  バイアス込みの+11.6%が、除去後は **ロングオンリー超過 +4〜5%/年（コスト後・税引前）** に縮小＝予想どおり上振れ分が剥落したが、ゼロにはならず。
- ✅ モメンタム/クオリティ単独は効かない（学術通り）。短期リバーサルは弱く残る。
- ⚠️ **DSR=0.674 で統計的断定には至らず**（valueの2軸が相関し試行数の壁）。ICIRは強いが、厳密な有意性は未達。
- ⚠️ 超過は**等加重ベンチ比**。真のTOPIX比較・税引後・実執行コストを入れると、無料インデックス(NISA)に対する正味の優位は数%・不確実。

→ **「バリューは本物だが控えめ」**。

## ①②の詰め（真TOPIX比較 / value傾斜合成 / LightGBM, PIT 2016–2024）

`scripts/run_backtest_pit.py`（①真TOPIX＋value傾斜）, `scripts/run_model_lgbm.py`（②Purged CV LightGBM）。

| 手法 | IC | ICIR | LSシャープ | 対TOPIX超過 |
|---|---|---|---|---|
| value_bp（単一） | 0.035 | 0.76 | 0.78 | +4.2% |
| **value_tilt（value0.4+ep0.4+rev0.2）** | **0.039** | **0.93** | **0.99** | +3.4% |
| LightGBM（9特徴量・Purged CV） | 0.020 | 0.55 | 0.55 | +0.6% |

**結論**:
- ✅ **単純な value傾斜合成が最良**（ICIR 0.93, LSシャープ 0.99）。
- ❗ **LightGBMは逆に悪化**。特徴量重要度がvalue/reversal/momに分散し、強いバリュー信号を希釈。
  「少数の効くファクター＋ノイズの多い月次クロスセクション」では**単純な加重合成がGBDTに勝つ**典型例。複雑化は過学習方向。
- DSR: 多重検定の試行数の数え方に依存（全ファクター11本込みで約0.76、最終3手法のみだと0.99）。
  いずれにせよ価格のみの0.53から大きく改善し、**valueのαは頑健**。

**最終評価**: バリュー傾斜のシンプル戦略が本命。対TOPIX超過は**コスト後・税引前で+3〜4%/年**（控えめだが本物）。
次は税引後/実執行を入れた到達点の見極めと、小額での実運用 or NISAインデックス主体かの判断。

## 投資シミュレーター（ブラウザ・実投資前の検証）

実投資の前に「もし自分がこう投資していたら」をブラウザで試せる。初期資金・保有銘柄数・
リバランス頻度・口座種別(NISA/課税)を変えると、過去データで資産推移・対TOPIX・税・最大DDを再現。
**100株単位・取引コスト・税(20.315%)を厳密に反映**（`app/analysis/simulate.py`）。

```bash
cd backend
../.venv/bin/python scripts/build_dashboard_data.py   # データ生成（sim_px/sim_scores/sim_topix 等）
../.venv/bin/uvicorn app.main:app                     # → http://127.0.0.1:8000
```
API: `GET /api/simulate?initial_capital=3000000&n_holdings=20&rebalance=Q&account=nisa`

### シミュレーション例（¥300万・20銘柄, 2016–2024）

| 口座×頻度 | 最終資産 | CAGR | 対TOPIX | 支払税 |
|---|---|---|---|---|
| **NISA・四半期** | **¥752万** | 12.0% | **+4.2%** | ¥0 |
| NISA・月次 | ¥695万 | 11.0% | +3.2% | ¥0 |
| 課税・年次 | ¥565万 | 8.1% | +0.3% | ¥89万 |
| 課税・月次 | ¥433万 | 4.6% | −3.1% | ¥132万 |
| 課税・月次・¥100万 | ¥111万 | 1.3% | −6.5% | ¥13万（平均5銘柄=分散不足） |

**シミュレーターが教えること**: NISA＋四半期リバランスが最適。課税口座×高頻度は税で優位が消滅。
小資金は100株単位制約で分散できず劣化。→ **NISA・低回転・¥5M+** が実運用の条件。

## サーバーで自動運用する

日次で「データ更新 → キャッシュ再生成 → 推奨スナップショット記録」を無人実行できる。
中身は `app/scheduler/jobs.py::daily_refresh`（平日18:30 JST）。

### 方法A: 常時稼働サーバー（推奨・APIも同時提供）
`KABUKA_ENABLE_SCHEDULER=1` で uvicorn を起動すると、プロセス内のAPSchedulerが日次実行。
```bash
KABUKA_ENABLE_SCHEDULER=1 ../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```
小さなVPS/クラウドVM（常時起動）に置けば、毎日自動で最新化＆実績記録が貯まる。

### 方法B: Docker（どこでも）
```bash
docker build -t kabuka backend
docker run -d -p 8000:8000 --env-file backend/.env -v kabuka-data:/app/data kabuka
```
`-v` でデータを永続化（reco_log等を保持）。スケジューラはイメージで既定ON。

### 方法C: cron（サーバーやMacの常駐なしで日次バッチだけ）
```cron
30 18 * * 1-5  cd /path/to/kabuka/backend && /path/to/.venv/bin/python -m app.scheduler.jobs
```
APIを使わず日次パイプラインだけ回したいとき。Macなら launchd でも可（電源ON時のみ）。

### 注意
- `.env`（J-Quants/EDINETキー）をサーバーに安全に配置する（コミットしない）。
- `data/` を永続ボリュームに（特に `reco_log.parquet` は再生成不可なライブ実績）。
- 手元Macは「電源ON時だけ」動く。毎日確実に貯めたいなら常時稼働のVPS/クラウドが必要。
