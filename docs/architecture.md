# アーキテクチャ設計

## 1. 全体構成

「バックエンドをAPIとして疎結合にする」ことを最重要の設計原則とする。
これにより、Webダッシュボード・将来のモバイルアプリ・自動売買ボットがすべて
同一のAPIを共有でき、ビジネスロジックの重複を避けられる。

```
┌─────────────────────────────────────────────────────────────┐
│  データソース                                                  │
│  J-Quants API / yfinance / ニュースRSS / マクロ指標            │
└───────────────┬─────────────────────────────────────────────┘
                │ (定期取得: APScheduler)
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Ingestion 層 (data fetchers)                                 │
│  - 株価(OHLCV) / 財務諸表 / マクロ / ニュース を正規化して保存  │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Storage 層  (PostgreSQL / TimescaleDB, 開発初期はSQLite)      │
│  prices, financials, macro, news, signals, predictions ...   │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│  Analysis 層                                                  │
│  - technical: テクニカル指標計算 (移動平均/RSI/MACD/一目 等)   │
│  - fundamental: 財務スコアリング / バリュエーション            │
│  - sentiment: ニュース・SNSのセンチメント分析 (LLM)           │
│  - prediction: 中長期(LightGBM等) / 短期 モデル              │
│  - signal: 上記を統合して売買シグナル生成                     │
│  - backtest: 戦略の過去検証 (リターン/リスク指標)            │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌─────────────────────────────────────────────────────────────┐
│  API 層  (FastAPI, REST + 将来WebSocket)                       │
│  /stocks /prices /indicators /predictions /signals /backtest │
└───────────────┬─────────────────────────────────────────────┘
                ▼
┌──────────────────┬──────────────────┬───────────────────────┐
│  Web (Next.js)   │ Mobile (将来:RN) │ 自動売買ボット(将来)    │

```

## 3. データモデル（初期案）

- `stocks` — 銘柄マスタ (code, name, market, sector, ...)
- `prices` — 日足OHLCV (code, date, open, high, low, close, volume, adj_close)
- `financials` — 財務 (code, fiscal_period, sales, op_income, net_income, equity_ratio, ...)
- `macro` — マクロ指標 (date, indicator, value)  例: 政策金利, 為替, GDP
- `news` — ニュース (id, code?, published_at, source, title, url, sentiment_score)
- `predictions` — 予測 (code, target_date, horizon, predicted_return, model, created_at)
- `signals` — シグナル (code, date, action[buy/sell/hold], score, rationale)
- `backtest_results` — バックテスト結果 (strategy, period, total_return, sharpe, max_dd, win_rate)

## 4. 予測アプローチ

- **段階的に**進める。最初から複雑なディープラーニングには行かない。
  1. **ベースライン**: テクニカル + 財務特徴量を入力に LightGBM で「N日後リターンの符号/分位」を予測（分類/回帰）
  2. 特徴量を拡充（マクロ、センチメントスコア）
  3. 必要に応じて時系列モデル（LSTM/Temporal Fusion Transformer 等）を比較検証
- **必ずバックテストで評価**。in-sample/out-of-sampleを分け、ウォークフォワード検証。
  リーク（未来情報の混入）を厳重に防ぐ。
- 評価指標: 年率リターン, シャープレシオ, 最大ドローダウン, 勝率, 取引コスト控除後リターン。

## 5. リスク・コストの扱い（目標の再定義）

**目標の再定義（2026-06-06 チーム調査後）**: 「年20%（または15%）」という**絶対リターン目標**は、
相場次第で達成/未達が決まり手法の良し悪しを判定できない。批判役の指摘に従い、目標を
**「反証すべき仮説」に格下げ**し、操作的に再定義する:

- 一次合格基準は絶対リターンではなく **「対TOPIX超過リターン(α)が偶然でない」**こと
  （Deflated Sharpe Ratio で有意か）。情報比(IR)も併用。
- 評価は**税引後・配当込み・ロングオンリー/ショート別・運用額前提**を明文化してから行う。
- 絶対20%/15%は、バックテストが結果として示す数値であって、先に決め打ちしない。
- バックテストには**取引コスト・スリッページ・税金**を必ず織り込む（コストbpsは楽観/中立/悲観でスイープ）。
- 過学習を警戒し、シンプルで頑健な戦略を優先。達成できない場合の **Go/No-Go 基準**をロードマップに埋める。

初回の無料データ検証では、単純な株価ファクターのシャープは（生存者バイアスで上振れしているはずの数値ですら）
1未満・税引前であり、絶対20%/15%は遠い。詳細は `backend/README.md`。

## 6. データソースの方針

**方針（2026-06-06 チーム調査後）**: 無料は「**実装当初**」の方針。機能が完成した後は月¥5,000程度まで
課金可なので、本検証では J-Quants Standard(¥3,300/月, 10年史+PIT補完)を採用する前提。
Premium(¥16,500/月)は配当金/先物/オプション/20年史が要る将来用で当面は見送り。
流れ: **まず¥0の無料スタックでMVP検証 → 完成後にStandardでPIT本検証**。

- **yfinance（無料・当面の主軸）**: `code.T` で株価を取得。`auto_adjust=True` で**配当・分割調整済**、
  10年以上のヒストリカルが取れる。J-Quants Freeは履歴が約2年と短く研究に不足するため、こちらを主軸に。
  ベンチマークは TOPIX連動ETF `1306.T`。
- **EDINET API（無料・公式）**: 金融庁。財務諸表(value/quality特徴量)を開示日付き(XBRL)で取得。
  リーク対策に有利。→ Phase 3 の特徴量拡充で導入。
- **J-Quants API（有望時に課金）**: 生存者バイアス回避に必須の **時点別構成銘柄(PIT)・上場廃止銘柄** の
  補完源。無料スタックで一次検証→αが出たら Standard で再検証、という二段構え。
- **無料スタックの既知の制約**: yfinanceは上場廃止銘柄が抜けるため**生存者バイアス**が残る。MVP結果は
  上振れ方向と理解し、合否判定は J-Quants でのPIT再検証まで保留する。
- **ニュース**: 各社IRのRSS、公開APIを利用。**利用規約を守り、無断スクレイピングはしない。**
- **マクロ**: 日銀・各種統計の公開データ。

## 7. セキュリティ・運用

- APIキー等は `.env` で管理し、リポジトリにコミットしない（`.gitignore`）。
- 自動売買（将来）は**最大の慎重さ**を要する。まずペーパートレード（仮想口座）で十分検証し、
  発注上限・損切りロジック・緊急停止を必須とする。証券会社APIの利用規約・本人確認も前提。

## 8. 確定パラメータ（2026-06-06 合意）

設計議論を経て、以下を初期パラメータとして確定した。

- **ユニバース（対象銘柄）**: 主要指数中心。まず **日経225** で軽く始め、安定したら TOPIX500 へ拡張。
- **予測ターゲット（中長期）**: **1〜3ヶ月先（約20〜60営業日後）のリターン**。
  まずは「上位/下位の分位に入るか」の分類、または期待リターンの回帰から始める。
- **デイトレ予測**: 後回し。中長期で基盤（データ・特徴量・バックテスト）を固めてから短期へ拡張。
- **運用形態**: まず **手元Macで都度実行**。ただし
  - 設定はすべて環境変数（`.env`）に外部化
  - 後で Docker 化・クラウド常時稼働へ移行しやすい構成
  を最初から守る。
- **Python**: 3.12（Homebrew導入済み）。
